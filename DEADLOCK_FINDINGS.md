**EXHAUSTIVE STATE-SPACE ANALYSIS NOT PERFORMED**

All reachability claims below concern witnessed directed executions or explicitly identified structural deductions. Endpoint binding searches inspect the current configuration; they do not enumerate its reachable state space, prove boundedness, or prove liveness. Time is the carried `currentTime` integer, not a clock that advances while waiting. Signatures are matching placeholder strings, not cryptography.

## Interpretation

- **Local deadlock:** an instance has no enabled local or synchronized transition while the rest of the system may still progress. A temporary peer wait also has no current binding; it is distinguished from a permanently blocked, unfinished instance.
- **Global deadlock:** no transition in the entire reachable configuration can fire. If this is because every activated lifecycle ended coherently, classify it as expected termination instead of a defect.
- **Expected termination:** successful or valid failure sinks, plus conditional peers that never received a request. A sink alone is not a deadlock finding.
- **Protocol wait:** a required peer event may still occur. **Permanent wait:** that event cannot occur again in this execution.
- A transition with a token and satisfied local guard can still lack a synchronous binding. Such a transition is **locally ready but disabled**, not literally “enabled-but-unsynchronizable.” No contradictory full-enabledness claim is made.
- A reference-reachable but inactive object is not an orphan. Root pool tokens retain the eight agents; EvidenceNet and CompetencyNet retain their created objects.

## Severity scale

S0 — no issue, expected terminal state; S1 — cosmetic/modeling clarity issue; S2 — peer remains waiting but does not invalidate the tested lifecycle; S3 — incomplete failure protocol; S4 — real deadlock affecting expected behavior; S5 — invalidates core model execution.

Rows are findings, **not a count of deadlocks in the state space**. S4 findings also have an S3 protocol cause, but are assigned the higher severity because the measured configuration cannot finish expected active work. No S5 invalidation of the nominal executable path was found. No S2 label is used to excuse unfinished Student, Wallet, or HR lifecycles. Intentional uninvoked services are S0.

## Recommendations only: minimum changes and tradeoffs

These are proposed design changes, not implemented edits or validated fixes. They must be rechecked for all timing alternatives before adoption. Changes that merely disable a failure branch, weaken signature equality, overwrite initial data, or declare unfinished active places terminal would hide the defect and are not recommended.

**R1 — Evidence-failure response (D01).** The existing Student rejection transition is a wallet credential-decision caller and cannot consume an evidence rejection correctly. Add one evidence-failure receiver transition from `StudentAgent.p_WaitingCredential` to existing `p_Rejected`, synchronized by `ProfessorAgent.t_RejectEvidence`. Pass the Student reference through the existing Student→Professor submit arguments (Student can supply `this`); this is a channel/arc-inscription extension. At the measured cutoff Student is still `p_Submitted`; its enabled `t_WaitCredential` can then release the professor notification. No new place is necessary. This is the smallest straightforward phase-correct receiver for this witness: one transition and its two arcs, plus existing interface inscriptions. It does not by itself resolve D02. A response outcome field should distinguish evidence rejection from later SBT rejection even if the sink is reused.

**R2 — Preserve the rejected assessment in EvidenceObject (D02).** The object's existing `t_Grade_Assign` has no passing-grade guard and outputs assessor, grade, and criteria. Add the already implemented `eo:evaluate(assessorDID,grade,criteriaURL)` call to `EvidenceNet.t_Reject`. It can record grade 40 at `p_Graded`, meaning “assessment recorded,” not “passed.” The existing `t_AssessEvidence` transaction already carries all arguments and the object is ready at `p_SubmittedLMS`. This is an inscription-only fix, with no new places/transitions/arcs. If the scientific specification requires a distinct object rejection status rather than a recorded failing grade, an explicit rejected place/transition is instead a minor topology change. This recommendation does not turn a failing grade into an approval.

**R3 — Abort reception for cancellation/expiry (D03).** The existing accept/reject chain cannot be reused unchanged after Competency has terminated: it requires the pending token and routes rejection back to Competency. For the witnessed post-consent states, add an abort receiver from Student `p_CredentialReceived` to `p_Rejected` and one from Wallet `p_PendingConsent` to `p_Rejected`; reuse a parameterized cancellation/expiry outcome channel. Synchronize those receivers with the existing Competency cancel/expire transition and object endpoint, passing the Student reference through existing interfaces as needed (Competency already holds Wallet). This requires two transitions and four arcs for the witnessed phase, no new places. A complete proposal must also handle cancellation **before** consent: either add receivers for the earlier active stages or explicitly gate cancellation on a modeled consent-ready handshake. Merely adding post-consent receivers could otherwise suppress currently allowed early cancellation. Outcome tokens should preserve whether failure was cancel or expiry.

**R4 — Signature-denial outcome (D04).** Keep the correct equality requirement on accept/reject. Add an explicit finite denial handshake, guarded by a mismatch against the credential's expected signature, that notifies Student/Wallet and terminates or records the attempted decision without accepting it. This needs a failure receiver path; the expected signature currently resides in CredentialObject, so a boolean denial/outcome must be carried back through the synchronous interfaces. Reuse existing failure sinks where their meaning is appropriate and introduce a distinct denial state only if the specification requires it. A retry design instead needs a new input source and retry path; replacing the fixed wrong signature with a correct initial value only removes the test and is not a fix. Valid cancellation may remain as an alternative, but must include R3 to release peers.

**R5 — Ledger-rejection propagation (D05).** Use the existing ledger reject branch to notify an active Competency failure receiver from `p_BlockchainAnchored` to `p_Terminated`, together with a credential failure receiver from `p_Anchored` to a failure sink and an HR failure receiver from `p_Parsed` to a distinct failure terminal (do not present `p_ResultReady` as a successful match). Carry outcome/reference data through existing inscriptions. This is a minor topology addition and can complete the witnessed execution. If the rejection synchronization waits for HR to reach `p_Parsed`, the currently enabled Student share and HR parse must remain available until that notification; alternatively buffer the ledger outcome in an explicit state. Both choices must be audited together with R6. There is no existing transition that can propagate this failure solely by changing a guard; weakening the aggregation guard cannot produce the missing ledger committed token. Other timing cases need corresponding early-stage reception or buffering.

**R6 — Commit-before-share semantics (D06).** Documentation alone can accurately say “acceptance initiated anchoring”; it cannot enforce successful anchoring. If the required behavior is that only ledger-validated/committed credentials can be shared, introduce a success/failure acknowledgement independent of the current HR-dependent `update_profile` aggregation and use it to release sharing or failure reception. Do **not** gate Student share on the existing `t_Agg_Ingest`/`t_Anchor`: aggregation needs HR `p_Parsed`, which requires that same share, creating a cycle. A coherent design can store the ledger outcome in Competency before releasing Student/Wallet, then allow HR parsing and final aggregation or error reporting. This requires a minor topology/synchronization extension with explicit outcome handling; a broader trust architecture redesign is not established as necessary by this audit. R5/R6 must be designed together, not combined as independent blocking handshakes.

## What was not established

Invalid issuer signature behavior was not simulated. An issuer mismatch would block the cancel channel structurally, but no measured final marking or S4/S5 severity is assigned to that unexecuted fixture. University rejection is an unreachable base branch, not a measured global deadlock. No orphan was observed. The nominal fixture still admits alternative cancel or ledger-reject choices: successful directed execution does not mean every schedule succeeds.
